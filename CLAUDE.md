# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

tuitok: TikTok's For You feed in the terminal, one upright video at a time, for one person's own use, playing inside Pepper (`../pepper`: Ghostty with video boxes). Rust, ratatui, tokio, MIT. A sibling of tuitube (`../tuitube`, YouTube), tuigram and tuimeta: the same security posture, themes and way of starting programs. When in doubt, do what tuitube does; its CLAUDE.md is the long version of most rules here. The research behind every choice, with measured numbers, is `reports/TikTok terminal client.md`: read it before changing how the feed is fetched or how videos play. The scripts that measured it are in `research_notes/spikes/` (Python: `uv run --no-project --with playwright python -I <script>`; raw numbers in `results/`).

## Decided

- **Logged out.** No TikTok account, login or cookie import. The feed is TikTok's logged-out For You (popular videos for the IP's country); the only cookies are the guest's the browser is given: `tt_chain_token`, which the video addresses need (403 without), and the rest, carried from batch to batch and from run to run (`guest.json`) so TikTok goes on with the same guest (a new guest repeated 6–8 of 13 videos from the batch before, the same guest none). The user asked for that, and for what was watched to be skipped in the next run: `tuitok --forget` starts over.
- **Own repository.** Pepper's README gets a paragraph about tuitok later, as it has for tuitube; nothing in Pepper changes for it.
- **A browser only while fetching.** The feed (`/api/recommend/item_list/`) needs signatures only TikTok's own JavaScript makes (a plain request gets HTTP 200 and no videos), so a headless browser opens `tiktok.com/foryou` and tuitok reads the `item_list` answers the page asks for, then closes it. Lightpanda first (0.13 s of CPU per video, ~290 MB, one process), Chrome as the fallback (~0.8 s, ~930 MB). The browser is the expensive part of tuitok: it runs only for a batch (about 15 s with Lightpanda), never for the whole time you watch.
- **No change to mpv or Pepper.** Videos are single MP4 files, not HLS or DASH; pepper-play loads Homebrew's libmpv, which plays them (H.265 up to 1080×1920 on the graphics chip).

## Status

All five steps of the report's "The plan" are done. What comes next is the user's call; noted on the way: Pepper's README paragraph about tuitok (the "PR for Pepper"), retrying a failed download (it streams instead now), and settings (a theme).

**The feed, as built (step 2).** `feed::fetch_any` tries `feed::engines` in order (Lightpanda, then Chrome) and returns the first `Batch` with videos, its `note` saying why any before failed. `feed::fetch` starts a `browser::Browser`, reads one batch and closes it. `browser.rs`: Lightpanda (`lightpanda serve --port 0`: it picks the 127.0.0.1 port and names it in its log, `browser::listening_port`; `--cdp-max-connections 1`, `--block-private-networks`, `LIGHTPANDA_DISABLE_TELEMETRY=true`) reached at `ws://127.0.0.1:PORT/` (the WebSocket straight away works; Playwright's `ws://` connect hung, its `http://` one didn't), Chrome with `CHROME_FLAGS` on two pipes as fds 3 and 4 (`as_fd3_and_4`, made under `tools::starting`); both in their own process group, `killpg` on close and in `Drop` (before the child is waited for, so its pid can't be reused), `kill_on_drop` too. `cdp.rs`: one client for both (`Cdp::websocket`, `Cdp::pipe`), `call` waits `CALL_WAIT`, `send` doesn't wait, messages capped at `MAX_MESSAGE`. `feed::read`: `Target.createTarget` a new page (Lightpanda's own first page doesn't navigate), attach with `flatten`, `Network.enable`, Chrome's user agent without `HeadlessChrome`, `NO_PLAY`, `Fetch.enable` with `refused()`, navigate; then each `Fetch.requestPaused` answered (`answer_paused`), feed answers (`is_feed`) read on `loadingFinished`, until `Ask::want` new videos, or `ENOUGH` and `QUIET`, or `LIMIT`; Chrome gets ArrowDown every `PRESS_AFTER` (Lightpanda loads more by itself and takes no keys); after each feed answer, until it has one, `Network.getCookies` for `tt_chain_token` (`feed::cookies`; `chain_token` checks it fits a header), and once it has it each answer's new videos go on at once through the `Tell` the caller gave (`feed::Found::hand_on`, each with the cookie; what's left without one goes at the end). The app gets them as `AppEvent::Found` and plays the first while the batch goes on (`App::add`; `App::found_so_far` for the status line, `App.batch_from`; `AppEvent::Batch` ends it): the page's first answer comes about 1.5 s after it opens, so the first video plays about 2.5 s after tuitok starts, where waiting for the whole batch took 14 s. A batch that fails after some videos came is those. `--feed` says when the first came (one batch of `feed::BATCH`). `video.rs`: `Video::parse` (lenient; `VideoId` 1–25 digits; text through `text::one_line` / `text::lines`, capped; renditions from `bitrateInfo`, H.264 and H.265 only, addresses through `video_url_allowed`, covers through `image_url_allowed`) and `Video::best`. Measured: Lightpanda 1.0.1 got 28–30 videos in 26–41 s; Chrome 12 in 41 s.

**Batches, as built.** A run's batches ask for `feed::SIZES` new videos (1, 2, 3, 5, 8, 13), one after another (`App::ramping`: `on_batch` starts the next), then `feed::BATCH` (13) each, started by `App::refill` once the video shown is the 8th of the last batch (`REFILL_AT`: 5 left after it). `App::next_ask` makes the `feed::Ask`: the batch's size (`App.batch_size`, for the status line) less what `App.spare` fills (videos past `want` in a batch's last answer: `Batch::spare`, handed on as the next batch's first; a batch the spare fills needs no browser), the run's `seen` ids (not counted, not handed on again), and the guest's cookies from the batch before (`Batch::cookies` → `App.cookies` → `Ask::cookies`, set with `Network.setCookies` before the page opens; Lightpanda takes them). Measured with Lightpanda: a batch of 1 ends at the page's first answer (1.6 s, 0.7 s of CPU), 13 take about 10 s (2.4 s of CPU); the 32 videos of the first six batches are in after about 25 s. `cargo test -- --ignored live_guest --nocapture` measures the repeats.

**Comments and the logo.** `comments.rs`: TikTok's comment list (`comments::url`: `www.tiktok.com/api/comment/list/?aid=1988&aweme_id=ID&count=10&cursor=0`) answers a plain request, unlike the feed: no signature, no cookie (20 videos tried: 7–10 of 10 back, 0.4–0.7 s as for 5, 23–40 KB). `App::want_comments` fetches them for the video shown and `COMMENTS_AHEAD` after it (`AppEvent::CommentsFetched` → `App.comments`; `App::prune` drops them with the covers); `ui::draw_panel` shows them last, under the counts, as many as fit (`Top comments`, `name · ♥ likes`, the text). `--demo` has made-up ones (`demo::comments`). If TikTok starts asking for signatures there too, the fetch fails and the panel shows none. The panel's border has tuitube's logo with TikTok's note for its play button: ` ♪ ` white on true black (`BADGE_BG`), then **tuitok**. Pepper reads kitty's text sizing (OSC 66) but ignores it, so no terminal text gets bigger than a cell. The video's side is boxed as tuitube's watch page is (`Areas::stage`, titled `▶ For You`), the video upright and centred in it; `f` drops the box and the panel.

**The downloads, as built (step 3).** `App::plan` decides, `App::prefetch` carries it out: the video shown and the `cache::AHEAD` after it, nearest first, `cache::PARALLEL` at a time, each `Video::best` for `App::box_pixels` (laid out by `ui::areas`, as drawn). Over `cache::DOWNLOAD_UP_TO` (by `DataSize`, or once that many bytes came) a video is `Download::Streams`, for step 4 to stream; one with nothing playable is `Failed`. `cache::download` tries each address of the rendition with Chrome's user agent, TikTok as referrer and its own batch's `tt_chain_token` (`Video.token`: every Lightpanda batch is a new guest), writes `<id>-<codec>-<w>x<h>.part` (0600, `create_new`), checks it starts as an MP4 (`ftyp`), renames it into place; progress comes back as `AppEvent::Progress`, the end as `AppEvent::Downloaded`. `App::prune` deletes the ones more than `cache::BEHIND` before the video shown. They live in the session's folder (`config::Session`: `session-<pid>` in the data folder, 0700, deleted at the end of the run, and by a later run once that pid is gone), so no video watched stays on disk (only its id, in `guest.json`). A download that failed isn't tried again yet.

**Playing, as built (step 4).** `main` picks what plays: pepper-play (`Tools.pepper_play`) when `pepper::port()` says tuitok runs in Pepper, else mpv in its own window (`player::Kind`). `App::start_player` starts it the first time something can play (`player::Player::start`: `OPTIONS`, the cleaned environment plus `PEPPER_PORT` for pepper-play, run from the home folder, its control socket as fd 3 under `tools::starting`, then over the socket: the three properties observed, the user agent and referrer, and for pepper-play its token, `pepper::new_token`, never on a command line). `App::play_current` (after `go`, a download's end, a batch) loads the video shown once `App::target` has one: its file once `Download::Ready`, else its address streamed (`Streams`, or a `Failed` download), the batch's cookie set as `http-header-fields` just before the `loadfile` and cleared for a file; while the video shown has nothing to play yet, the player is stopped. Each video loops (`--loop-file=inf`). What mpv says comes back as `AppEvent::Player` with the player's number (`App.players`; an older player's words are dropped): `Restarted` marks the video shown as playing (`App.playing`), position, length and pause go to the panel, `Failed` says why, `Exited` (the window closed, or it ended) forgets the player, and the next play starts another. In Pepper, after each frame `App::placement` places the picture over the box (`ui::areas`, laid out from `App.size`) while the video shown plays, places it again when the box moves, and takes it away otherwise; `ui` draws the box black then, and says `Loading…`, `Playing in mpv's window` or why it can't play otherwise. Quitting takes the box away and gives the player `QUIT_GRACE` to quit. Keys: `space` pause, `m` mute, `h`/`l` and ←/→ seek `SEEK` seconds, only while the video shown plays.

**Covers, the demo and the rest (step 5).** `covers.rs`: `covers::picker` gives Ghostty, Pepper and kitty (by their environment) kitty's protocol with the cell size from `TIOCGWINSZ`, without asking: `Picker::from_query_stdio` leaves its stdin reader behind when nothing answers, and it takes the next key; other terminals are asked, else half blocks. `App::want_covers` (after a batch, a move, a resize, `f`, and each cover's step) fetches the covers of the video shown and the `cache::AHEAD` after it (`Video.cover`: `originCover`, else `cover`; `covers::fetch`: `image_url_allowed`, `MAX_BYTES`, JPEG only within `limits`, decoded on a blocking thread with a panic `contained`, which `main::start_screen`'s panic hook lets pass) and encodes each fetched one for `ui::cover_area` (`covers::encode`, again when that size changes); `App::prune` drops them with the downloads. `ui::draw_in_box` draws the cover with `TEXT_ROWS` of text under it, or the text alone while there's none; in Pepper while the video plays, nothing (the picture is over the box). `f` (`App::toggle_fullscreen`): in Pepper the box takes all but the bottom line (`ui::areas`'s `fullscreen`), elsewhere mpv's `cycle fullscreen`. The panel's position line has a progress bar (`ui::progress`). `--demo` (`demo.rs`, `App::demo`): made-up videos and covers drawn in code, the cover over the whole box, a made-up position; `App.demo` keeps it from fetching, playing or pruning the covers. SIGHUP and SIGTERM quit as `q` does (`App::run`), so the player quits, Pepper's box goes and the session's folder is deleted.

## Commands

```sh
cargo build
cargo test                    # offline tests
cargo clippy --all-targets    # keep it warning-free
cargo fmt
cargo run -- --check          # what tuitok found: Pepper, pepper-play, Lightpanda, Chrome, mpv
cargo run -- --feed           # one batch of the feed, listed (--feed lightpanda | chrome for one)
cargo run -- --demo           # made-up videos: nothing fetched or played
cargo test -- --ignored live  # fetches a batch with each browser found
```

UI tests render into ratatui's `TestBackend` (`ui.rs`). Tests never start programs or write Pepper's sequences. Tests that talk to TikTok, run a browser or mpv are `#[ignore]`d (`cargo test -- --ignored live`; mpv with no picture or sound, `player::Kind::Headless`). To run the whole app without a window or sound: `TUITOK_MPV="$PWD/tools/mpv-silent"`, and `tools/drive.py` runs it in a pseudo-terminal, presses keys and prints the screen through pyte (ratatui redraws only cells that changed, so raw output can't be searched). Pepper's box itself needs a person in a Pepper tab: never point tests at the Pepper you're in.

`docs/hero.png`, the README's picture, is one frame of `--demo` in Pepper: `cargo test -- --ignored export_hero_screen` writes `target/hero/` (every cell, where the cover goes, the cover at 1080×1920), and `uv run --no-project --with pillow --with fonttools python -I tools/hero.py target/hero docs/hero.png ../pepper/src/font/res` draws it as Pepper would (Ghostty's own JetBrains Mono, and its fallbacks for ♪ ♫ ♥ and emoji), with a made-up frame of the video in the box (tuitube's `tools/hero.py`, cut down). Redraw it when the screen changes.

At run time: `brew install mpv lightpanda-io/browser/lightpanda`; Chrome is the fallback. `tools::Tools::find` resolves each program once to an absolute path (`TUITOK_PEPPER_PLAY`, `TUITOK_LIGHTPANDA`, `TUITOK_CHROME`, `TUITOK_MPV`, else `PEPPER_PLAY`, `PATH`'s absolute folders, Homebrew's, `/Applications`); a program is never started by bare name. `main` cuts `PATH` to its absolute folders before any thread starts.

## Security

As tuitube's, where it applies:

- Everything from TikTok is untrusted: captions, names, the feed's JSON (read leniently, every field optional), image bytes, addresses. Text is cleaned of control characters and capped before it's shown or stored; ids are checked where they come in; paths and errors printed go through `tools::shown`.
- Nothing private goes on a command line (`ps` shows them to every user). `tt_chain_token` stays in tuitok's memory and `guest.json` (0600) with the guest's other cookies. It goes to pepper-play or mpv only over their socket, as `http-header-fields`, for a video streamed rather than downloaded. The guest's other cookies stay in memory too (`App.cookies`), only TikTok's domains, names and values fit for a header, at most `MAX_COOKIES` (`feed::guest_cookies`), and go only to the next batch's browser (`Network.setCookies`, over Chrome's pipe or Lightpanda's 127.0.0.1 socket; never Lightpanda's `--cookie` file) and to `guest.json`. `guest.rs`: in the data folder (0700, checked), written as `guest.json.part` (`create_new`, 0600) then renamed into place when a run ends (`App::carry_out`: the last batch's cookies, the ids watched up to the furthest shown, the newest `MAX_WATCHED`); read back only if a plain file of yours under `MAX_BYTES`, the cookies through `feed::guest_cookies` again and expired ones dropped, the ids through `VideoId::new` (`App::carry_in` puts them in `seen`). `--check` counts them, `--forget` deletes the file; `--feed` and `--demo` don't touch it.
- Video and image addresses are fetched only over https from TikTok's hosts (seen: `v16-webapp-prime.tiktok.com`, `v19-webapp-prime.tiktok.com`); `www.tiktok.com` addresses in `UrlList` are skipped, as yt-dlp does. `cache::client` follows redirects only to those hosts (at most 2), takes no proxy from the environment (the browser gets none either), keeps no cookies and sends no referrer of its own; a download must answer 200, start as an MP4 and stay under `DOWNLOAD_UP_TO`.
- The browser: a profile in a 0700 folder in tuitok's data folder, kept between batches of a session, deleted on exit; images, fonts, and fetch/XHR answers holding video or sound refused (TikTok streams through MediaSource, so refusing "Media" alone stops nothing), and `play()` a no-op. Lightpanda runs with `LIGHTPANDA_DISABLE_TELEMETRY=true` and serves its DevTools on 127.0.0.1, which local programs (other accounts too) can reach, so it picks the port itself (`--port 0`, read from its log: none can take the port first and be handed tuitok's connection and cookies), takes one client (`--cdp-max-connections 1`: a second gets HTTP 503, tested; one that got in first leaves tuitok refused before a cookie is sent, and Chrome fetches), keeps its pages off private and local addresses (`--block-private-networks`), and runs only for a batch. Accepted: a video streamed rather than downloaded is fetched by mpv, which follows redirects anywhere with the cookie (it has no option to stop that; reqwest's downloads follow only TikTok's hosts), so a redirect off TikTok's CDN could see the logged-out guest token, nothing more. Chrome is driven over `--remote-debugging-pipe` (no port). Lightpanda is AGPL-3.0: a separate program, never linked or bundled.
- pepper-play and mpv are controlled over a socketpair passed as fd 3 (`--input-ipc-client=fd://3`): no socket file (and macOS caps those paths at 104 bytes), and mpv's IPC can run programs. Pepper's token goes to pepper-play only over that socket; `OSC 777;pepper` sequences are written only when `pepper::port()` is set (Pepper, not through a multiplexer: `pepper::MULTIPLEXERS` is tmux, GNU screen, zellij and herdr, which sets `HERDR_PANE_ID`; through one, the box isn't placed, videos play in mpv's window, and the panel and `--check` name the multiplexer, `pepper::behind_multiplexer`). Found the hard way: in herdr, which sets none of the others, tuitok placed a box Pepper never got. The box is filled with `Color::Rgb(0, 0, 0)`, never `Color::Black`, which is the palette's colour 0 (grey in Catppuccin).
- What's typed is never echoed back raw (`main` doesn't repeat unknown arguments).
- Comments: only from `comments::url` (a checked id in a fixed address) through `cache::client(comments::url_allowed)` (https on `www.tiktok.com` only, redirects too), no cookie, at most `MAX_BYTES`, read leniently, names and text cleaned and capped like captions, kept in memory only.
- Covers: only from TikTok's image hosts, at most `covers::MAX_BYTES`, JPEG only (no PNG or WebP decoder runs on what TikTok sends), within `covers::limits`, a decoder panic contained; kept in memory, never on disk.
- SIGHUP (the window closed) and SIGTERM end tuitok as `q` does, so nothing of the run is left behind.
- tmux (`tmux.rs`, tuitube's): ratatui-image's picker runs `tmux set -p allow-passthrough on`; `tmux::save` reads the pane's own value before `covers::picker` and `tmux::restore` puts it back on the way out (after the run, after `--demo`, in the panic hook). `covers::picker` never forces kitty's protocol through a multiplexer, even when `TERM_PROGRAM` still says Ghostty there: it asks, and ratatui-image wraps the pictures for tmux.
