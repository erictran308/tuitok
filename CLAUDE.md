# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

tuitok: TikTok's For You feed in the terminal, one upright video at a time, for one person's own use, playing inside Pepper (`../pepper`: Ghostty with video boxes). Rust, ratatui, tokio, MIT. A sibling of tuitube (`../tuitube`, YouTube), tuigram and tuimeta: the same security posture, themes and way of starting programs. When in doubt, do what tuitube does; its CLAUDE.md is the long version of most rules here. The research behind every choice is under "Research, in short" below: read it before changing how the feed is fetched or how videos play. The full report is `reports/TikTok terminal client.md` and the scripts that measured it are in `research_notes/spikes/` (Python: `uv run --no-project --with playwright python -I <script>`; raw numbers in `results/`): both gitignored, on this computer only, not on GitHub; a fresh clone has them in the first commit (`git show 6d903ff:'reports/TikTok terminal client.md'`).

## Decided

- **Logged out.** No TikTok account, login or cookie import. The feed is TikTok's logged-out For You (popular videos for the IP's country); the only cookies are the guest's the browser is given: `tt_chain_token`, which the video addresses need (403 without), and the rest, carried from batch to batch and from run to run (`guest.json`) so TikTok goes on with the same guest (a new guest repeated 6–8 of 13 videos from the batch before, the same guest none). The user asked for that, and for what was watched to be skipped in the next run: `tuitok --forget` starts over.
- **Own repository.** Nothing in Pepper changes for it, its README included: no "PR for Pepper" (the user's call, 2026-10-16).
- **A browser only while fetching.** The feed (`/api/recommend/item_list/`) needs signatures only TikTok's own JavaScript makes (a plain request gets HTTP 200 and no videos), so a headless browser opens `tiktok.com/foryou` and tuitok reads the `item_list` answers the page asks for, then closes it. Lightpanda first (0.13 s of CPU per video, ~290 MB, one process), Chrome as the fallback (~0.8 s, ~930 MB). The browser is the expensive part of tuitok: it runs only for a batch (about 15 s with Lightpanda), never for the whole time you watch.
- **No change to mpv or Pepper.** Videos play as whole MP4 files (long videos' DASH renditions, the picture alone, are left out; no HLS); pepper-play loads Homebrew's libmpv, which plays them (H.265 up to 1080×1920 on the graphics chip).

## Research, in short

Measured on 2026-10-16 (Apple M5 Pro, macOS 27.2, Chrome 156), the way Pepper's own bench measures (`pepper-play/bench/measure.py`: CPU as a share of one core, memory as Activity Monitor's footprint).

- **The feed needs TikTok's own JavaScript.** A plain GET of `/api/recommend/item_list/?from_page=fyp` answers HTTP 200 with `{"status_code":0}` and no videos (it wants X-Bogus / msToken signatures); TikTokApi got 0 videos; no signing without a browser was viable. A browser on `tiktok.com/foryou` gets the `recommend` and `preload` `item_list` answers, logged out. Only `tt_chain_token` is needed for the video addresses (403 without), and it works from a plain client after the browser closes. Comments (`/api/comment/list/`) need no signature.
- **What it costs.** TikTok in a Chrome window: 49.1% (95th percentile 74.9%), 1,524 MB (peak 2,263). Headless Chrome as it is: 34.1%, 1,011 MB; lean (video, sound, images, fonts refused, `play()` a no-op): 13.5%, 654 MB. pepper-play with a 576×1024 clip: 10.1%, 219 MB; Pepper itself meanwhile 5.1%; a ratatui app with kitty images: 2.5%, 40 MB. TikTok streams video through fetch into MediaSource, so lean mode must refuse video and audio content types at the response stage.
- **Browsers, one batch each.** Lightpanda 1.0.1: 27–28 videos in 14 s, 3.4 s of CPU, 288 MB peak (it takes no key events but loads more by itself; its own first page doesn't navigate; Playwright's `ws://` connect hung). Chrome Headless Shell: 10–13 in 42 s, 8.6 s, ~500 MB. Chrome: 13 in 42 s, 10–11 s, ~925 MB. WebKit: 13 in 43 s, 11 s, 830–950 MB. Firefox (Playwright's) wouldn't launch. Lightpanda is AGPL-3.0: run, never linked.
- **Search and links (2026-10-17, `reports/Search and links.md`).** Logged out, TikTok answers keyword search (`/api/search/item/full/`, `/api/search/general/full/`) and hashtag pages (`/api/challenge/item_list/`) with HTTP 200 and no body, in Lightpanda, headless Chrome and Chrome in a window alike; a creator's videos (`/api/post/item_list/`) with a slider captcha (`bdturing-verify`). So no search without an account. Explore's categories work without a browser: `GET /explore` sets `ttwid` (which `/api/explore/item_list/?aid=1988&categoryType=N&count=16` needs; without it `statusCode` 100001) and `tt_chain_token`, then each page is 13–16 new videos in 0.5–0.7 s (five in a row: 74 different). A pasted link works without a browser too: a plain GET of `https://www.tiktok.com/@_/video/ID` holds the video in `__UNIVERSAL_DATA_FOR_REHYDRATION__` (`webapp.video-detail.itemInfo.itemStruct`, the feed's shape) and sets `tt_chain_token`; short links (`vt.tiktok.com/…`) are one 301 to it (a live one: 0.2 s). Built: "Links, as built" below.
- **Videos.** Progressive MP4 renditions in `bitrateInfo` (h264, h265_hvc1, ByteDance's bytevc2, which is left out); H.265 1080×1920 (1.48 MB) was smaller than the default H.264 576×1024 (2.52 MB). mpv's first frame: 0.23 s from a file, 0.2–0.9 s streamed with the cookie set over IPC. Videos on `v16-webapp-prime.tiktok.com` / `v19-…` (`www.tiktok.com` addresses skipped); covers on `p16` / `p19-common-sign.tiktokcdn.com` as JPEG (`originCover` about a third of `cover`'s size; `dynamicCover` is animated WebP).

**The downloads, as built (step 3).** `App::plan` decides, `App::prefetch` carries it out: the video shown and the `cache::AHEAD` after it, nearest first, `cache::PARALLEL` at a time, each `Video::best` for `App::box_pixels` (laid out by `ui::areas`, as drawn). Over `cache::DOWNLOAD_UP_TO` (by `DataSize`, or once that many bytes came) a video is `Download::Streams`, for step 4 to stream; one with nothing playable is `Failed`. `cache::download` tries each address of the rendition with Chrome's user agent, TikTok as referrer and its own batch's `tt_chain_token` (`Video.token`: every Lightpanda batch is a new guest), writes `<id>-<n>-<codec>-<w>x<h>.part` (0600, `create_new`; `n` the download's number in the run, so one stopped half way never shares a file with the next of that video; the `.part` goes however the download ends, `cache::Part`), checks it starts as an MP4 (`ftyp`), renames it into place; progress comes back as `AppEvent::Progress`, the end as `AppEvent::Downloaded`, each with the download's number (`App.underway`, `App::is_underway`: what one stopped since says is dropped). `App::prune` deletes the ones more than `cache::BEHIND` before the video shown. A download of a video no longer among the one shown and the `AHEAD` after it stops (`App::cancel_unwanted`, from `prefetch`), so those get their turn; a mark (to stream, or nothing playable) takes no turn. The video shown waits `STREAM_AFTER` (1 s) for its download, under way or waiting its turn, then streams and its download stops (`App::wait_to_stream`, `AppEvent::Waited`, `App::stream_instead`). Videos more than `KEPT_BEHIND` (100) before the one shown are forgotten (`App::forget_behind`: they count as watched, their ids stay in `seen`, `k` goes back no further). They live in the session's folder (`config::Session`: `session-<pid>` in the data folder, 0700, deleted at the end of the run, and by a later run once that pid is gone), so no video watched stays on disk (only its id, in `guest.json`). A download that fails is tried again (`App::try_again_later`, `AppEvent::TryAgain`): after `cache::retry_after` (3 s, then 6 s), `cache::TRIES` in all (`App.failures`); meanwhile the video streams if it's shown, and one playing streamed isn't downloaded as well (`App::try_again`). A video with nothing playable (`Step::Mark`) isn't tried again.

**Playing, as built (step 4).** `main` picks what plays: pepper-play (`Tools.pepper_play`) when `pepper::port()` says tuitok runs in Pepper, else mpv in its own window (`player::Kind`). `App::start_player` starts it the first time something can play (`player::Player::start`: `OPTIONS`, the cleaned environment plus `PEPPER_PORT` for pepper-play, run from the home folder, its control socket as fd 3 under `tools::starting`, then over the socket: the volume and mute (`player::Sound`), five properties observed, the user agent and referrer, and for pepper-play its token, `pepper::new_token`, never on a command line). `App::play_current` (after `go`, a download's end, a batch) loads the video shown once `App::target` has one: its file once `Download::Ready`, else its address streamed (`Streams`, or a `Failed` download), the batch's cookie set as `http-header-fields` just before the `loadfile` and cleared for a file, and `pause` set off (mpv keeps it from one file to the next); while the video shown has nothing to play yet, the player is stopped. Each video loops (`--loop-file=inf`). What mpv says comes back as `AppEvent::Player` with the player's number (`App.players`; an older player's words are dropped): what it says of a file names the playlist entry it played it as (`player::Heard`: each `loadfile` carries its number as `request_id`, mpv's answer names the entry it made, `PlayerEvent::Loaded` → `App.entry`, and `playback-restart` and positions belong to the last `start-file`'s), so what the file before says as it loops or ends just after the next was loaded is dropped. `Restarted` marks the video shown as playing (`App.playing`), position (said as the whole second changes: mpv says one each frame, and each is a redraw), length and pause go to the panel, `Failed` says why (only for the video shown: `play_error` is cleared when the next can't play yet), `Exited` (the window closed, or it ended) forgets the player, and none starts again until a key asks (`App.player_gone`: `j`, `k` or a feed picked; the box says `The player closed: j or k plays on`). In Pepper, after each frame `App::placement` places the picture over the box (`ui::areas`, laid out from `App.size`) while the video shown plays, places it again when the box moves, and takes it away otherwise; `ui` draws the box black then, and says `Loading…`, `Playing in mpv's window` or why it can't play otherwise. Quitting takes the box away and gives the player `QUIT_GRACE` to quit. Keys: `space` pause and `h`/`l`, ←/→ or `,`/`.` seek `SEEK` seconds, only while the video shown plays; `m` mute and `-`/`+` (or `=`) the volume by `VOLUME_STEP`, any time, as tuitube's (`App::set_muted`, `App::set_volume`: a change unmutes). The player starts as loud as `App.volume` and `App.muted` say (`player::Sound`, set over the socket before `volume` and `mute` are observed), and follows them from mpv's window too (`PlayerEvent::Volume`, `Muted`). The panel's position line says `volume N%` only when it isn't 100, and `muted` in `warning`. The volume is kept in settings.toml when tuitok ends, if it changed (`App::keep_volume`, from `main`); muting is for the run.

**Settings, as built.** `settings.rs`: `settings.toml` in the data folder, as tuitube's: `theme` (an id of `theme::BUILT_IN`; `theme::id` gives the default for any other), `volume` (0 to 100), and `pause_on_unplug` and `animations` (on unless `false`). `settings::load` is lenient (each setting that isn't right is its default; a file that isn't a plain file of yours, is over `MAX_BYTES` or isn't TOML gives the defaults); `settings::save` changes one key in the file as it is now, so what else it holds stays, and leaves a file that doesn't read alone. `main` hands them to `App::use_settings` with the data folder; `--demo` reads them but saves nothing. `?` (`App::open_help`) opens `App.help`, a `HelpMenu`, the popup tuitube has: a Keys tab (`ui::KEYS`, every key; `j`/`k`, `g`/`G` scroll it, `HelpMenu.scroll` a `Cell` that `ui::draw_help` keeps in range) and a Settings tab, tuitube's rows (`HelpMenu::PAUSE_ON_UNPLUG` and `ANIMATIONS`, `[✓]` when on, under ` Playing` and ` Look`; then from `HelpMenu::THEMES` the themes, `theme::names()`, the one in use dotted, the cursor on it when the popup opens). Tab, `h`/`l` or ←/→ switch tabs; on Settings, `j`/`k` move and Enter or Space turns the setting under the cursor on or off, or picks the theme under it, and saves it at once (`App::toggle_pause_on_unplug`, `App::toggle_animations`, `App::pick_theme`, through `App::save_setting`; an error shows under the themes), the popup staying open; Esc, `q` or `?` close it; Ctrl-C still quits, other keys do nothing meanwhile (`App::on_help_key`). `ui::draw_help` draws it centred over everything, its own keys in its bottom border. While it's open Pepper's picture has a hole for it or is taken away ("Holes, as built"), and on terminals whose pictures paint over text (`App::pictures_paint_over`: sixel, iTerm2's) the cover isn't drawn, as in tuitube. `ui::hints` leaves out whole the bottom line's hints that don't fit, never the last (`q quit`).

**Covers, the demo and the rest (step 5).** `covers.rs`: `covers::picker` gives Ghostty, Pepper and kitty (by their environment) kitty's protocol with the cell size from `TIOCGWINSZ`, without asking: `Picker::from_query_stdio` leaves its stdin reader behind when nothing answers, and it takes the next key; other terminals are asked, else half blocks. `App::want_covers` (after a batch, a move, a resize, `f`, and each cover's step) fetches the covers of the video shown and the `cache::AHEAD` after it (`Video.cover`: `originCover`, else `cover`; `covers::fetch`: `image_url_allowed`, `MAX_BYTES`, JPEG only within `limits`, decoded on a blocking thread with a panic `contained`, which `screen::set_panic_hook` lets pass) and encodes each fetched one for `ui::cover_area` (`covers::encode`, again when that size changes); `App::prune` drops them with the downloads. With kitty's protocol each encode is sent under a number of tuitok's own (`covers::KittyIds`, from a random start; otherwise as the picker's `new_protocol` makes it) and deleted from the terminal once it's dropped, wherever that happens (`KittyImage`'s `Drop`: pruned, encoded again at a new size, failed, the feed changed, quitting), the deletions written before each frame and all of them on the way out (`App::send_deletions`): the terminal keeps every picture until told, about 16 MB a cover, and past its 320 MB drops the ones sent first. `ui::draw_in_box` draws the cover with `TEXT_ROWS` of text under it, or the text alone while there's none; in Pepper while the video plays, nothing (the picture is over the box). `f` (`App::toggle_fullscreen`): in Pepper the box takes all but the bottom line (`ui::areas`'s `fullscreen`), elsewhere mpv's `cycle fullscreen`. The panel's position line has a progress bar (`ui::progress`). `--demo` (`demo.rs`, `App::demo`): made-up videos and covers drawn in code, the cover over the whole box, a made-up position; `App.demo` keeps it from fetching, playing or pruning the covers. SIGHUP and SIGTERM quit as `q` does (`App::run`, which takes them before any task starts), so the player quits, Pepper's box goes and the session's folder is deleted. A task's panic (tokio catches it and the event loop would go on, drawing on a terminal the hook put back) leaves the screen as it is and sends tuitok SIGTERM, so it quits that way too and says why after (`screen::set_panic_hook`, `screen::task_panic`, `main::ended`); only the event loop's own panic hands the terminal back at once, then unwinds (so the browser is still killed by its `Drop`). A resize keeps the cell size found before if the terminal doesn't say. Comments', Explore's and covers' answers are read through `cache::read_capped` (`Content-Length` first, then as they come).

## Commands

```sh
cargo build
cargo test                    # offline tests
cargo clippy --all-targets    # keep it warning-free
cargo fmt
cargo run -- --check          # what tuitok found: Pepper, pepper-play, Lightpanda, Chrome, mpv
cargo run -- --feed           # one batch of the feed, listed (--feed lightpanda | chrome for one)
cargo run -- --demo           # made-up videos: nothing fetched or played
cargo run -- LINK             # that video first, then For You
cargo test -- --ignored live  # fetches a batch with each browser found
cargo test -- --ignored unplugging  # switches the sound's output for a few seconds (output.rs)
```

UI tests render into ratatui's `TestBackend` (`ui.rs`). Tests never start programs or write Pepper's sequences. Tests that talk to TikTok, run a browser or mpv are `#[ignore]`d (`cargo test -- --ignored live`; mpv with no picture or sound, `player::Kind::Headless`). To run the whole app without a window or sound: `TUITOK_MPV="$PWD/tools/mpv-silent"`, and `tools/drive.py` runs it in a pseudo-terminal, presses keys and prints the screen through pyte (ratatui redraws only cells that changed, so raw output can't be searched). Pepper's box itself needs a person in a Pepper tab: never point tests at the Pepper you're in.

`docs/hero.png`, the README's picture, is one frame of `--demo` in Pepper: `cargo test -- --ignored export_hero_screen` writes `target/hero/` (every cell, where the cover goes, the cover at 1080×1920), and `uv run --no-project --with pillow --with fonttools python -I tools/hero.py target/hero docs/hero.png ../pepper/src/font/res` draws it as Pepper would (Ghostty's own JetBrains Mono, and its fallbacks for ♪ ♫ ♥ and emoji), with a made-up frame of the video in the box (tuitube's `tools/hero.py`, cut down). Redraw it when the screen changes.

At run time: `brew install mpv lightpanda-io/browser/lightpanda`; Chrome is the fallback. `tools::Tools::find` resolves each program once to an absolute path (`TUITOK_PEPPER_PLAY`, `TUITOK_LIGHTPANDA`, `TUITOK_CHROME`, `TUITOK_MPV`, else `PEPPER_PLAY`, `PATH`'s absolute folders, Homebrew's, `/Applications`); a program is never started by bare name. `main` cuts `PATH` to its absolute folders before any thread starts.

## Security

As tuitube's, where it applies:

- Everything from TikTok is untrusted: captions, names, the feed's JSON (read leniently, every field optional), image bytes, addresses. Text is cleaned of control characters and capped before it's shown or stored; ids are checked where they come in; paths and errors printed go through `tools::shown`.
- Nothing private goes on a command line (`ps` shows them to every user). `tt_chain_token` stays in tuitok's memory and `guest.json` (0600) with the guest's other cookies. It goes to pepper-play or mpv only over their socket, as `http-header-fields`, for a video streamed rather than downloaded. The guest's other cookies stay in memory too (`App.cookies`), only TikTok's domains, names and values fit for a header, at most `MAX_COOKIES` (`feed::guest_cookies`), and go only to the next batch's browser (`Network.setCookies`, over Chrome's pipe or Lightpanda's 127.0.0.1 socket; never Lightpanda's `--cookie` file) and to `guest.json`. `guest.rs`: in the data folder (0700, checked), written whole through `config::write_private` (`guest.json.<pid>.part`, `create_new`, 0600, renamed into place, so two runs ending together don't touch each other's) when a run ends (`App::carry_out`: the last batch's cookies, the ids watched up to the furthest shown, the newest `MAX_WATCHED`); read back only if a plain file of yours under `MAX_BYTES`, the cookies through `feed::guest_cookies` again and expired ones dropped, the ids through `VideoId::new` (`App::carry_in` puts them in `seen`). `--check` counts them, `--forget` deletes the file; `--feed` and `--demo` don't touch it.
- Video and image addresses are fetched only over https from TikTok's hosts (seen: `v16-webapp-prime.tiktok.com`, `v19-webapp-prime.tiktok.com`); `www.tiktok.com` addresses in `UrlList` are skipped, as yt-dlp does. `cache::client` follows redirects only to those hosts (at most 2), takes no proxy from the environment (the browser gets none either), keeps no cookies and sends no referrer of its own; a download must answer 200, start as an MP4 and stay under `DOWNLOAD_UP_TO`.
- The browser: a profile in a 0700 folder in tuitok's data folder, kept between batches of a session, deleted on exit; images, fonts, and fetch/XHR answers holding video or sound refused (TikTok streams through MediaSource, so refusing "Media" alone stops nothing), and `play()` a no-op. Lightpanda runs with `LIGHTPANDA_DISABLE_TELEMETRY=true` and serves its DevTools on 127.0.0.1, which local programs (other accounts too) can reach, so it picks the port itself (`--port 0`, read from its log: none can take the port first and be handed tuitok's connection and cookies), takes one client (`--cdp-max-connections 1`: a second gets HTTP 503, tested; one that got in first leaves tuitok refused before a cookie is sent, and Chrome fetches), keeps its pages off private and local addresses (`--block-private-networks`), and runs only for a batch. Accepted: a video streamed rather than downloaded is fetched by mpv, which follows redirects anywhere with the cookie (it has no option to stop that; reqwest's downloads follow only TikTok's hosts), so a redirect off TikTok's CDN could see the logged-out guest token, nothing more. Chrome is driven over `--remote-debugging-pipe` (no port). Lightpanda is AGPL-3.0: a separate program, never linked or bundled.
- pepper-play and mpv are controlled over a socketpair passed as fd 3 (`--input-ipc-client=fd://3`): no socket file (and macOS caps those paths at 104 bytes), and mpv's IPC can run programs. Pepper's token goes to pepper-play only over that socket; `OSC 777;pepper` sequences are written only when `pepper::port()` is set (Pepper, not through a multiplexer: `pepper::MULTIPLEXERS` is tmux, GNU screen, zellij and herdr, which sets `HERDR_PANE_ID`; through one, the box isn't placed, videos play in mpv's window, and the panel and `--check` name the multiplexer, `pepper::behind_multiplexer`). Found the hard way: in herdr, which sets none of the others, tuitok placed a box Pepper never got. The box is filled with `Color::Rgb(0, 0, 0)`, never `Color::Black`, which is the palette's colour 0 (grey in Catppuccin).
- What's typed is never echoed back raw (`main` doesn't repeat unknown arguments; the command lines show what's typed or pasted without `text::is_hidden` characters, which aren't taken, and their errors never quote it).
- Links: only a video's id or a short link's code is kept from what's typed, pasted or given to `tuitok LINK` (`links::parse`: TikTok's hosts only, no user, password or port, at most `MAX_LINK`), and what's fetched is built from it, never the link: `links::page_url` through the `www.tiktok.com` client, no cookie sent; a short link rebuilt on its own host and asked with `cache::client(|_| false)`, which follows no redirect (its `Location` is parsed as a link again and must be a video's, `links::leads_to`). A page is at most `links::MAX_BYTES`, read as the feed's (`Video::parse`); its `tt_chain_token` stays in memory as the video's token (downloads, or the player's socket). The video's id goes into `seen`, and once shown into `guest.json`'s watched ids, as the feed's do.
- Comments: only from `comments::url` (a checked id in a fixed address) through `cache::client(video::www_url_allowed)` (https on `www.tiktok.com` only, redirects too), no cookie, at most `MAX_BYTES`, read leniently, names and text cleaned and capped like captions, kept in memory only.
- Explore: only `explore::PAGE` and `explore::url` (a category of the fixed `CATEGORIES`, never typed text) through the same `www.tiktok.com` client. The guest's `ttwid` and `tt_chain_token` are taken from `Set-Cookie` only if they fit a header, kept in memory only (`App.explore_guest`, never in `guest.json`), `ttwid` sent back only to `www.tiktok.com`, `tt_chain_token` only as the feed's token is (downloads, or the player's socket). An answer is at most `explore::MAX_BYTES` and read as the feed's (`Video::parse`). What's typed in the bar only filters the fixed list: it's never sent anywhere, and `text::is_hidden` characters aren't taken.
- Covers: only from TikTok's image hosts, at most `covers::MAX_BYTES`, JPEG only (no PNG or WebP decoder runs on what TikTok sends), within `covers::limits`, a decoder panic contained; kept in memory, never on disk.
- settings.toml is read as guest.json is (a plain file of yours, at most `settings::MAX_BYTES`; the TOML parser's own message isn't shown, as it quotes the file) and written the same way (`config::write_private`: `settings.toml.<pid>.part`, `create_new`, 0600, renamed into place). It holds only the theme, the volume, `pause_on_unplug` and `animations`.
- SIGHUP (the window closed) and SIGTERM end tuitok as `q` does, so nothing of the run is left behind; so does a task's panic (SIGTERM to itself). The terminal (`screen.rs`, tuitube's) is taken over and handed back by tuitok's own code, not `ratatui::init`/`restore`, which print failures with `eprintln!` (a panic when stderr is a closed tab; one in the panic hook aborts: closing the tab used to end tuitok with SIGABRT, the guest unsaved and the session's folder left). A closed tab's terminal fails every write with EIO, even of nothing (`screen::gone`): then nothing is put back, and stdout, and stderr if it was that terminal, go to /dev/null, so what's written on the way out can't fail. A frame or a key read that fails because the tab is gone is a quit too, and the player quits whatever happened. Tested by closing a pseudo-terminal under `--demo`: exit 0 (SIGABRT before).
- tmux (`tmux.rs`, tuitube's): ratatui-image's picker runs `tmux set -p allow-passthrough on`; `tmux::save` reads the pane's own value before `covers::picker` and `tmux::restore` puts it back on the way out (after the run, after `--demo`, in the panic hook). `covers::picker` never forces kitty's protocol through a multiplexer, even when `TERM_PROGRAM` still says Ghostty there: it asks, and ratatui-image wraps the pictures for tmux.
